# 竞品分析 — API 风险监测报告模板与生成

> 数据来源：公开官网/产品文档/官方演示页，整理日期：2026-04-23。  
> 分析焦点：`API 风险监测` 场景下的 **内置报告模板**、**模板自定义**、**报告生成/导出**、**风险洞察呈现方式**。  
> 说明：部分厂商公开资料更强调“仪表盘/合规视图/数据导出”，未必直接公开“报告模板编辑器”细节，相关能力需在正式选型或产品演示中进一步验证。

## 分析范围

- 目标能力：
  1. 支持内置多个报告模板
  2. 支持报告模板自定义
  3. 支持基于 API 风险监测结果生成报告
- 选择竞品：
  - [Akamai API Security](https://www.akamai.com/products/api-security)
  - [Salt Security](https://salt.security/)
  - [深信服 DASP / NGAF 相关能力](https://www.sangfor.com.cn/sangfor-security/dasp)

| 一键生成正式报告 | 必须 | △ 有 dashboard + export + reporting API，偏“数据导出与合规视图” | △ 更偏洞察视图和资源输出，未看到“一键正式报告生成”明确表述 | ✓ 明确提到“一键输出应用安全检测报告” |
| 报告导出格式 | 重要 | ✓ JSON / CSV，且支持异步、分页、多维度查询 | △ 公开页未明确导出格式 | △ 报告输出明确，但导出格式公开材料较少 |

| 与工单 / SIEM / 外部系统联动 | 重要 | ✓ Jira / SIEM / ITSM / Grafana 等联动较强 | △ 强调治理策略与平台整合 | ✓ 可通过 RESTful API 获取威胁/日志供外部系统消费 |

## 逐家分析

### 1. Akamai API Security

#### 公开能力摘要

- 产品页明确强调：
  - 自动发现 API 资产、影子 API、敏感数据暴露
  - 持续监测 API 漏洞、行为异常、数据泄露和滥用
  - 与 WAF、SIEM、ITSM、CI/CD 联动
- 官方演示中明确展示了三类关键视图：
  - API Inventory 列表视图
  - Runtime incident / evidence 视图
  - Compliance Dashboard / Security Dashboard
- Reporting API v2 进一步证明其“报告能力”并非只停留在固定仪表盘：
  - 支持多维分组
  - 支持异步查询、分页
  - 支持按指标、维度、时间范围灵活取数
  - 支持 JSON / CSV 输出

#### 对报告产品的启示

- Akamai 的强项不是“富文本报告编辑器”，而是：
  1. **标准化框架视图**：直接把 OWASP / PCI DSS 等框架做成可切换的合规视图
  2. **从摘要到证据的下钻**：总览分数 -> findings -> incident -> request/response evidence
  3. **报告 API 化**：允许外部系统按需拼装自己的报告
- 这意味着它在“**报告生成链路**”上比较成熟，但“**模板化排版与品牌定制**”不一定是核心卖点。

#### 值得借鉴

1. 报告模板应至少区分：
   - 管理层摘要模板
   - 合规审计模板
   - 技术处置模板
2. 模板不应只是静态 PDF，而应绑定：
   - 指标选择
   - 时间范围
   - 风险等级过滤
   - 事件范围过滤
3. 允许“视图模板”与“导出模板”分离：
   - 视图模板用于平台内查看
   - 导出模板用于对外汇报

### 2. Salt Security

#### 公开能力摘要

- 强调 API Discovery 是起点：
  - 自动发现内部、外部、第三方 API
  - 提供参数、使用模式、风险分数、敏感数据暴露等 granular details
  - 强调 context-rich filtering / querying
  - 支持姿态治理（Posture Governance）与合规
- Resource Center 很强，说明其“研究内容输出”多，但这些更多是市场内容，不等于平台内的报告模板能力。

#### 对报告产品的启示

- Salt 的公开表述更偏“**自定义洞察**”而非“固定报告模板”：
  - 用户先有 API 全景与上下文数据
  - 再通过过滤/查询形成自定义风险洞察
  - 最后把洞察用于治理、策略和响应
- 对我们来说，这说明“报告模板”不能只做静态章节编排，还应支持：
  1. 选择分析对象（API / 应用 / 账号 / IP / 标签）
  2. 选择风险视角（姿态 / 运行时 / 敏感数据 / 合规）
  3. 选择输出颗粒度（摘要 / 明细 / 证据）

#### 值得借鉴

1. 在报告模板设计里保留“**洞察组件化**”思路：
   - API 资产总览卡
   - 风险趋势图
   - 敏感数据分布图
   - Top 风险 API / Top 风险账号 / Top 异常来源
2. 模板编辑器不要只支持改标题和 Logo，更要支持“选择组件 + 组件参数”。
3. 报告生成前，允许基于同一模板做“范围裁剪”，比如：
   - 仅导出高风险项
   - 仅导出指定业务系统
   - 仅导出近 7 天异常事件

### 3. 深信服 DASP / NGAF

#### 公开能力摘要

- DASP 产品页明确出现：
  - 一站式应用安全检测工具链 AST
  - 一键输出应用安全检测报告
  - 输出 SBOM
  - 安全能力通过 API / SDK 方式集成
- 社区资料显示：
  - NGAF RESTful API 可用于提取安全威胁、URL 访问日志、流量与规则相关数据
  - 更适合被外部平台二次消费、拼接成自定义报表

#### 对报告产品的启示

- 深信服路线更像“**安全平台 + 固定报告输出 + 开放 API**”：
  1. 平台原生提供若干标准报告
  2. 更复杂的自定义报表通过 API 数据外送实现
- 这条路线对政企/审计类客户很实用，因为：
  - 标准报告能快速交付
  - API 能满足定制集成
- 但如果做产品化程度更高的“模板中心”，仍有空间可做得更细。

#### 值得借鉴

1. 首版就应内置几类“能直接交付客户”的标准报告：
   - 应用/API 风险概览报告
   - 检测结果明细报告
   - 合规检查报告
   - 整改闭环跟踪报告
2. 每份报告最好支持“一键生成 + 导出”，降低一线安全运营成本。
3. 对外开放报告数据 API，支持客户二次集成 BI / SOC / 审计系统。

## 关键差异总结

| 维度 | Akamai | Salt Security | 深信服 |
|---|---|---|---|
| 报告视图成熟度 | 最强，仪表盘与合规视图公开证据最完整 | 强在洞察与治理，上下文分析突出 | 强在标准检测报告与接口导出 |
| 模板化程度 | 中等，更像“标准 dashboard + Reporting API” | 偏弱，公开资料中更像“分析视图 + 过滤查询” | 中等，偏固定标准报告 |
| 自定义能力 | 强，API 级取数和多维过滤较成熟 | 强，过滤与策略治理强 | 中等，更多靠 API 和项目化集成 |
| 适合作为我们参考的方向 | “报告 API + 合规模板 + 证据下钻” | “洞察组件化 + 灵活分析范围” | “标准报告快速交付 + 数据开放能力” |

## 对本产品的需求启发

### P0：必须具备

1. **内置多模板中心**
   - 至少内置 4 类模板：
     - 管理层摘要
     - API 风险运营日报 / 周报
     - 合规审计报告
     - 技术事件明细报告
2. **模板参数化**
   - 时间范围
   - 业务系统 / 应用范围
   - API 分组
   - 风险等级
   - 事件类型
   - 数据标签范围
3. **一键生成正式报告**
   - 支持立即生成
   - 支持导出 PDF / Word / HTML（至少 PDF）
   - 保留生成历史与版本
4. **报告证据链**
   - 报告中的聚合结果必须能追溯到：
     - API
     - 账号 / IP
     - 告警事件
     - 请求 / 响应数据标签
5. **组件化模板结构**
   - 模板由可复用组件拼装：
     - 摘要指标
     - 趋势图
     - 风险分布
     - Top 榜单
     - 事件时间线
     - 证据明细表

### P1：建议尽快规划

1. **模板自定义编辑器**
   - 支持增删模块
   - 支持排序
   - 支持配置组件参数
   - 支持预览
2. **合规映射模板**
   - 例如 OWASP API Top 10 / PCI / 等保 / 内部审计要求
3. **计划任务生成**
   - 支持日报 / 周报 / 月报自动生成与分发
4. **多角色输出**
   - 管理层看摘要
   - 安全运营看事件
   - 开发/应用负责人看整改项

### P2：可形成差异化

1. **品牌化报告输出**
   - 自定义封面、Logo、页眉页脚、术语口径
2. **模板版本管理**
   - 草稿 / 已发布 / 归档
   - 发布记录与变更说明
3. **报告对比**
   - 不同时间窗口对比
   - 不同业务系统对比
   - 不同环境（生产 / 测试）对比
4. **外部接口**
   - 对外暴露报告元数据与结果 API
   - 便于接入 BI、审计或 SOC 平台

## 差异化机会点

1. **竞品多数更强在“仪表盘”或“固定检测报告”，不是“报告模板中心”**
   - 机会：把“API 安全分析结果”真正产品化成“模板中心 + 生成中心 + 历史中心”

2. **竞品对“模板自定义”的公开表达普遍不够强**
   - 机会：将模板能力做成低代码化，允许安全运营人员自行组合组件与参数

3. **竞品普遍强调 API 风险发现和响应，但对“对外汇报交付”重视不足**
   - 机会：把对内研判和对外汇报统一成一套报告资产体系

## 结论与建议

如果本产品要同时覆盖“安全运营使用”和“对内外汇报交付”，建议路线不要只学单一竞品：

- **Akamai** 适合借鉴：`合规视图 + 安全视图 + Reporting API + 证据下钻`
- **Salt Security** 适合借鉴：`上下文洞察 + 组件化分析视图 + 灵活过滤`
- **深信服** 适合借鉴：`标准报告快速产出 + 开放 API 供二次集成`

因此，推荐本产品的核心设计方向是：

> **“模板中心 + 组件化分析模块 + 一键生成 + 历史版本 + 对外导出”**  
> 而不是只做一个静态导出按钮，或只做一个无法复用的固定报表页面。

## Handoff 给 Stage 1 的输入

### 建议优先覆盖的用户场景

1. 安全运营人员按周输出“API 风险运营周报”
2. 应用负责人查看某业务系统的“高风险 API 整改报告”
3. 审计/管理层查看“季度 API 风险与合规汇总报告”

### Stage 1 需要继续验证的问题

1. 报告的主要读者是谁？管理层、安全运营、开发负责人是否要分模板？
2. 模板自定义要做到什么程度？仅配置字段，还是支持拖拽编排？
3. 报告生成是离线任务还是同步即时导出？
4. 是否需要多租户/多品牌/多项目独立模板体系？
5. 是否需要与审批、归档、发送、签章等流程集成？
